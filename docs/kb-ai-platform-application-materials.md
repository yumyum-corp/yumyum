# KB국민은행 AI·플랫폼개발 지원 소재 정리

> 기준일: 2026-09-09
> 목적: 자소서 문장이나 흐름이 아닌, 냠냠코치 프로젝트에서 꺼낼 수 있는 기술 소재와 검증 가능한 수치 정리
> 주의: 팀 프로젝트 수치는 본인이 실제 담당한 범위를 확인한 뒤 사용한다.

---

## 1. 용어와 구현 범위

현재 냠냠코치에는 하나의 `멀티 에이전트 RAG 챗봇`이 구현된 것이 아니라 다음 두 기능이 분리되어 있다.

- **F703 RAG 기반 개인화 영양 챗봇**: 식품 지식 검색과 Member의 당일 식단을 결합해 근거가 포함된 답변 생성
- **F704 멀티 에이전트 주간 코칭**: 7일간의 식단·운동·체중을 역할별 Agent가 분석하고 최종 코칭으로 종합

정확한 표현:

- `RAG 기반 개인화 영양 질의응답 기능`
- `역할 분리형 멀티 에이전트 주간 코칭 파이프라인`
- `구조화된 기록 상태를 판정하는 규칙 기반 Agent 동적 라우팅`
- `Nutrition Agent 내부 조건부 RAG와 Agent별 장애 격리`
- `검색 출처와 개인 식단 데이터를 결합한 프롬프트 구성`

피해야 할 표현:

- `자율형 멀티 에이전트 구현`
- `LLM 리더 Agent가 동적으로 업무를 분배`
- `MCP/Tool Calling 기반 Agent`
- `멀티 에이전트 RAG 챗봇 구현`
- `RAG로 환각을 제거`
- `대화 이력을 기억하는 멀티턴 챗봇`

## 2. F703 RAG 기반 개인화 영양 챗봇

### 해결하려던 문제

- 일반 LLM은 Member의 실제 식단을 알지 못해 일반적인 답변만 생성한다.
- 모델 자체 지식에만 의존하면 식품 영양정보를 근거 없이 생성할 수 있다.
- 식품 정보와 개인 섭취 현황을 함께 제공해 근거성과 개인화를 동시에 확보하고자 했다.

### 전체 처리 흐름

```text
Vue 질문
  → Spring POST /chat
  → 인증정보에서 memberId 추출
  → 당일 식단 + 활성 Program + HealthGoal 조회
  → 개인 식단 context 생성
  → FastAPI POST /ai/chat
  → 질문 임베딩 및 ChromaDB 유사도 검색
  → 검색 문서 + 개인 식단 + 질문으로 프롬프트 조립
  → LLM 호출
  → answer + sources 반환
```

### 개인화 컨텍스트

총 9개 요소를 LLM에 전달한다.

1. 당일 섭취 칼로리
2. 목표 칼로리
3. 당일 단백질
4. 목표 단백질
5. 당일 탄수화물
6. 목표 탄수화물
7. 당일 지방
8. 목표 지방
9. HealthGoal: `DIET`, `MUSCLE`, `HEALTH`, `DISEASE`

동일한 질문이라도 섭취량과 목표량에 따라 답변이 달라질 수 있다. 수치 기반 판단의 예시는 `현재 단백질 39g / 목표 120g = 달성률 32.5%`이다.

### 검색 구조

- Vector DB: ChromaDB `PersistentClient`
- Collection: `nutrition`
- Embedding: `paraphrase-multilingual-MiniLM-L12-v2`
- 현재 지식 베이스: 식품 25개
- 질문당 후보 문서: 최대 3개
- 관련도 필터: L2 거리 1.5 이하만 컨텍스트에 포함
- Collection이 비어 있을 때만 JSON 지식 베이스 적재
- 디스크 영속화를 사용해 재시작 시 중복 임베딩 방지

### Top-K 이후 임계값 필터를 추가한 이유

- Top-K 검색은 관련성이 낮아도 항상 K개 문서를 반환한다.
- 무관한 문서가 프롬프트에 들어가면 모델이 이를 근거처럼 사용하는 검색 노이즈가 발생한다.
- 최대 3개를 검색하되 L2 거리 1.5를 초과한 문서를 제거해 문서 수보다 관련성을 우선했다.
- 적절한 문서가 없으면 `sources=[]`를 반환한다.

### 프롬프트 구조

```text
[역할]
영양 전문 AI 코치

[참고 식품 정보]
검색된 최대 3개 문서

[사용자 오늘 식단]
실제 섭취량 / 목표량 / HealthGoal

[질문]
사용자 자연어 질문
```

### 응답과 근거 노출

- `answer`: LLM의 최종 답변
- `sources`: 검색에 사용한 식품명과 영양정보
- 답변만 반환하지 않고 출처를 별도 필드로 제공해 사용자가 참고 근거를 확인할 수 있게 했다.

### 장애 대응과 관측성

- 활성 Program이 없거나 식단 컨텍스트 생성이 실패하면 `context=null`로 질문을 계속 처리한다.
- ChromaDB 검색 실패 시 `sources=[]`로 LLM 호출을 계속한다.
- `ENV=dev`에서는 외부 API 비용 없이 mock 응답을 사용한다.
- 모든 LLM 호출에 대해 모델, 지연시간, 입력·출력 토큰, 추정 비용, 오류를 구조화 로그로 기록한다.

### 현재 한계

- 지식 베이스 25개는 데모 수준이다.
- 관련도 임계값 1.5는 평가 데이터가 아닌 경험적 값이다.
- 답변 문장과 개별 출처가 직접 연결되지는 않는다.
- 검색 실패 시 모델 자체 지식으로 계속 답하므로 환각 위험이 남는다.
- 이전 대화 내역을 요청에 포함하지 않아 엄밀한 멀티턴 챗봇은 아니다.
- 의료·질환 관련 질문의 별도 안전 정책과 답변 거부 기준이 부족하다.

### 개선 후보

- 식품안전처 기반 지식 베이스를 300개 이상으로 확대
- Precision@K, Recall@K, MRR로 retrieval 품질 측정
- 임계값 1.5를 평가 결과에 따라 튜닝
- 근거 없는 문장은 생성하지 않도록 groundedness 검증 추가
- 답변 문장별 출처 연결
- 대화 세션과 이전 대화 요약 도입
- 질환 관련 질문에 전문가 상담 고지 및 고위험 답변 제한
- 검색 실패 시 일반 답변을 허용하는 질문과 답변을 거부할 질문 분리

## 3. F704 멀티 에이전트 주간 코칭

### 해결하려던 문제

- 식단·운동·체중 데이터를 하나의 긴 프롬프트로 처리하면 각 영역의 분석이 피상적일 수 있다.
- 서로 다른 도메인의 데이터를 역할별로 분석하고, 중간 결과를 다시 종합해 교차 해석의 품질을 높이고자 했다.

### Agent 구성

1. **영양 Agent**
   - 7일 칼로리 및 단백질 섭취 분석
   - 목표 대비 평균 달성률과 부족 패턴 해석
2. **운동 Agent**
   - 운동별 성공 세트/전체 세트, 평균 수행 중량 분석
   - 주간 운동 성과 요약
3. **목표 Agent**
   - 영양·운동 분석, 주당 체중 추세, HealthGoal을 결합
   - 현재 목표 달성 궤도 평가
4. **Synthesis Agent**
   - 세 분석 결과의 중복과 충돌을 정리
   - 다음 주 실천 방향을 포함한 4~5문장 코칭 생성

### 실제 실행 구조

```text
WeeklyCoachingRequest
  → CoachingFacts 계산
  → 규칙 기반 CoachingRouter
  → 선택된 Nutrition·Exercise Agent (둘 다 선택되면 asyncio.gather)
  → 체중 추세 또는 교차 분석이 필요할 때 Goal Agent
  → 전문 Agent가 하나 이상이면 Synthesis Agent
```

- 전문 Agent: 3개, 통합 Agent: 1개
- Nutrition 선택 기준: 실제 영양값이 양수인 날짜 1일 이상
- Exercise 선택 기준: `total_sets > 0`인 운동 기록 1개 이상
- Goal 선택 기준: 체중 추세 존재 또는 Nutrition·Exercise 동시 선택
- Nutrition 내부 RAG: 비교 가능한 평균 영양소 달성률 중 하나가 80% 미만일 때만 실행
- 기록 없음: LLM 0회, 결정론적 안내 문구 반환
- 최대 LLM 호출: 4회
- 영양·운동 동시 선택 시 실행 임계경로: 3단계
- 분석 범위: 7일
- 최종 응답 필드: 7개

이 Router는 LLM Supervisor가 아니다. 자연어 판단을 추가 호출로 위임하지 않고 구조화된 데이터의 존재와 계산된 추세를 순수 함수로 판정하므로 동일 입력에 동일한 실행 경로를 선택한다.

### Nutrition Agent의 조건부 RAG

- 목표값이 0인 영양소는 부족률 비교에서 제외한다.
- 단백질·탄수화물·지방 평균 달성률 중 가장 낮은 값을 우선 영양소로 정한다.
- 80% 미만이면 `{HealthGoal 한글명} 목표, {우선 영양소} 보충에 적합한 한식 식품`으로 검색한다.
- 기존 ChromaDB의 최대 3개, L2 거리 1.5 이하 정책을 재사용한다.
- 동기 검색은 `asyncio.to_thread()`로 이벤트 루프 밖에서 실행한다.
- 검색 실패는 빈 근거로 격리하고 Nutrition·전체 코칭을 계속한다.
- 검색 문서가 있을 때만 Nutrition 프롬프트의 `[참고 식품 정보]`에 추가한다.

### LLM과 결정론적 계산의 분리

코드가 직접 계산하는 값:

- 일별 칼로리 달성률
- 7일 평균 칼로리 달성률
- 목표 달성일 수
- 주당 체중 변화량

LLM이 담당하는 값:

- 영양 패턴 해석
- 운동 성과 해석
- 목표 달성 가능성 설명
- 최종 자연어 코칭

목표 달성일은 칼로리 달성률이 목표의 80~120%인 날로 계산한다. 정확한 수치 계산은 코드가 맡고, LLM은 비정형 해석과 설명에 집중한다.

### Spring의 7일 데이터 집계

- Program 시작일로 주차의 시작일과 종료일 계산
- 날짜별 칼로리·단백질·탄수화물·지방 집계
- 날짜별 운동 소모 칼로리 집계
- `sessionId + exerciseName` 기준으로 운동 세트 그룹화
- 운동별 성공 세트 수, 전체 세트 수, 평균 중량 계산
- 날짜별 체중 기록 조회
- Program 목표 영양소와 HealthGoal 결합

### 배치 기반 생성

- Program 시작 후 7일 이상 지난 Member 대상
- `programId + weekNumber`로 기존 WeeklyReport 확인
- 중복 리포트가 없을 때 stub을 먼저 생성
- FastAPI 멀티 에이전트 분석 호출
- 결과를 WeeklyReport에 저장
- 사용자는 앱 진입 시 미리 생성된 리포트를 조회

실시간 요청에서 최대 4회의 LLM 호출을 기다리게 하지 않고, 주간 배치에서 품질 중심 분석을 수행하도록 분리했다.

### 장애 격리

- 생략된 Nutrition: `분석 미실행: 해당 주차 영양 기록이 없습니다.`
- 생략된 Exercise: `분석 미실행: 해당 주차 운동 기록이 없습니다.`
- 생략된 Goal: `분석 미실행: 체중 추세 또는 교차 분석 데이터가 부족합니다.`
- 영양 Agent 실패: `영양 분석 불가`
- 운동 Agent 실패: `운동 분석 불가`
- 목표 Agent 실패: `목표 분석 불가`
- Synthesis 실패: 고정 fallback 코멘트
- 체중 추세 계산 실패: `null`
- 운동 기록 없음: `이번 주 운동 기록 없음`
- 전체 기록 없음: Agent와 LLM을 호출하지 않고 데이터 부족 안내 반환
- RAG 검색 실패: 빈 근거로 Nutrition 분석 계속
- FastAPI 전체 호출 실패: Spring에서 경고 로그를 남기고 기존 stub 유지

일부 Agent 실패가 전체 배치 중단으로 전파되지 않도록 단계별 fallback을 적용했다.

### 최종 응답 7개 필드

1. 최종 통합 코칭
2. 영양 분석 요약
3. 운동 분석 요약
4. 목표 분석 요약
5. 평균 칼로리 달성률
6. 목표 달성일 수
7. 주당 체중 변화량

### 현재 한계

- 규칙 기반 동적 라우팅이며 자연어 의도를 해석하는 LLM Supervisor는 아니다.
- Tool Calling과 MCP를 사용하지 않는다.
- RAG는 Nutrition Agent의 영양소 부족 경로에서만 사용한다.
- 동일비중 fixture 결과는 실제 운영 트래픽 평균이 아니다.
- 실제 API 3회 탐색 측정은 수행했지만 축약된 고정 DAG 프롬프트와 RAG 의존성 누락 때문에 비용·토큰 수치를 성과로 사용할 수 없다.
- Agent별 품질 평가셋과 응답 정확도 지표가 없다.
- Spring의 WeeklyReport stub은 AI 호출 실패 후 자동 재시도되지 않는다.

### 개선 후보

- 고위험 조언을 검증하는 Critic/Verifier Agent 추가
- Agent별 정확도와 최종 groundedness 평가셋 구축
- 운영 데이터 분포로 Agent 선택률과 비용 재계측
- timeout, retry, circuit breaker 적용
- 실패한 WeeklyReport의 재처리 큐 또는 보상 배치 추가
- Agent별 latency, token, cost, fallback rate 대시보드 구축

## 4. F703과 F704 비교

| 구분 | RAG 영양 챗봇 | 멀티 에이전트 코칭 |
|---|---|---|
| 목적 | 근거가 포함된 개인화 질의응답 | 복합 데이터의 역할별 분석 |
| 실행 시점 | 사용자 질문 시 실시간 | 주간 배치 |
| 주요 입력 | 질문, 검색 문서, 당일 식단 | 7일 식단·운동·체중 |
| LLM 호출 | 1회 | 기록 조합에 따라 0~4회 |
| 외부 지식 검색 | ChromaDB 사용 | Nutrition 부족 조건에서만 ChromaDB 사용 |
| 개인화 범위 | 당일 섭취량과 목표 | 일주일간 행동과 추세 |
| 결과 | 답변과 출처 | 분야별 분석과 통합 코칭 |
| 오케스트레이션 | 단일 RAG 파이프라인 | 규칙 기반 동적 라우팅 |

## 5. 검증 가능한 정량 소재

### RAG 챗봇

- 지식 베이스: 25개 식품 문서
- 검색 결과: 최대 3개
- 관련도 임계값: L2 거리 1.5
- 개인화 컨텍스트: 9개 요소
- LLM 출력 상한: 500 tokens
- RAG·Chat 관련 테스트: 20개

### 멀티 에이전트 코칭

- 전문 Agent 3개 + Synthesis 1개
- 병렬 실행 Agent: 2개
- LLM 호출: 기록 조합에 따라 0~4회
- 실행 임계경로: 3단계
- 분석 데이터: 7일
- 달성 인정 범위: 목표의 80~120%
- 응답 필드: 7개
- 동적 라우팅·RAG·서비스·API 관련 테스트: 46개
- 동일비중 8개 fixture × 3회 mock 비교에서 평균 실행 Agent: 4.0 → 2.5, 37.5% 감소
- 같은 비교에서 평균 LLM 호출: 3.0 → 2.5, 16.7% 감소
- 평균 mock 지연: 36.500ms → 35.125ms, p90: 47.000ms → 47.000ms
- 실제 API 3회 탐색 결과: 평균 지연 11.104초 → 8.673초, 요청당 비용 $0.004276 → $0.004094
- 실제 API 수치는 표본 부족, 축약된 고정 DAG 프롬프트, RAG fallback 때문에 잠정 참고값이며 성과로 주장하지 않는다.

### 전체 AI 서버

- FastAPI 라우트: 14개
- pytest: 197개 통과
- 실제 테스트 결과: `197 passed in 15.03s` (2026-09-09 실행)

동적 라우팅 수치는 기록 없음, 영양만, 운동만, 체중만, 영양+체중, 운동+체중, 영양+운동, 전체 데이터의 8개 fixture를 같은 비중으로 사용하고 각 3회 반복한 탐색 비교다. 호출당 10ms 고정 지연 mock의 호출 수 감소는 결정론적 검증값으로 사용할 수 있지만 지연은 실제 모델 성능으로 표현하지 않는다. 실제 API도 같은 표본으로 실행했으나 보정 전 비교이므로 비용 절감률은 주장하지 않는다.

정량 수치는 단순 구현 개수보다 `어떤 위험을 검증했는지`와 함께 제시하는 편이 좋다. 예: 빈 체중 기록, 운동 기록 없음, 검색 실패, Agent 호출 실패, 잘못된 입력, 응답 스키마를 자동화 테스트로 검증했다.

## 6. KB AI 에이전트 뱅킹과의 기술적 접점

- 자연어 질문을 업무에 연결: RAG 검색 및 향후 의도 라우팅
- 전문 Agent 분리: 검색·조회·이체·상담별 책임 분리 가능
- 생성과 실행의 경계: 금융 수치와 거래는 LLM이 생성하지 않고 검증된 API가 수행해야 함
- 근거 노출: 상품설명서·약관·FAQ·업무규정 출처 제공
- 부분 장애 격리: 검색 또는 특정 Agent 장애가 전체 서비스로 전파되지 않게 설계
- 관측성: Agent별 지연시간, 토큰, 비용, 오류, fallback 비율 추적
- 금융 안전성: 최소 권한, 거래 전 재확인, 감사 로그, 고위험 답변 차단 필요

## 7. 추가로 활용 가능한 프로젝트 소재

### A. 외부 AI 호출과 핵심 트랜잭션 분리

- 온보딩 트랜잭션 커밋 후 `AFTER_COMMIT + @Async`로 Program 생성
- FastAPI 실패가 Member 온보딩을 롤백시키지 않도록 장애 경계 설정
- 기존 3~5초 외부 AI 대기를 사용자 요청 경로에서 제거
- Program 준비 상태는 프론트에서 2초 간격, 최대 6회 폴링
- 한계: 실패 자동 재시도는 아직 없음

**강점 키워드:** 트랜잭션 경계, 비동기 처리, 장애 격리, 사용자 응답성

### B. AI가 필요 없는 곳에서 AI를 제거한 의사결정

- 온보딩 직후에는 사용자 행동 데이터가 없어 진정한 개인화가 불가능하다고 판단
- `/ai/plan/generate`의 LLM 호출을 목표별 템플릿으로 교체
- 응답시간을 3~5초에서 수십 ms 수준으로 단축
- 개인화 AI는 데이터가 쌓이는 홈 코멘트와 WeeklyReport에 집중

**강점 키워드:** AI 과잉 적용 방지, 비용·지연 최적화, 문제 중심 설계

### C. Redis 12시간 캐시와 DB 커넥션 보호

- 홈 AI 코멘트를 `home_comment:{memberId}` 키로 Redis에 12시간 저장
- Cache HIT 시 즉시 반환, MISS일 때만 FastAPI 호출
- 이력이 필요 없는 일시적 데이터를 DB에 저장하지 않아 스키마 추가 방지
- Redis 장애 시 FastAPI 직접 호출로 서비스 유지
- 최대 15초 HTTP 대기 중 DB 커넥션이 점유되지 않도록 서비스 전체의 `@Transactional` 제거

**강점 키워드:** 캐싱, 비용 절감, 커넥션 풀 보호, 수평 확장

### D. Vision 식단 분석 평가 체계

- 음식명 Precision·Recall·F1 측정
- 섭취량과 칼로리 오차를 MAPE로 측정
- 평균 latency와 p90 latency 측정
- API 실패 건수와 호출 비용 측정
- 프롬프트 A/B 및 모델 비교가 가능한 평가 스크립트 구현
- 실제 평가 데이터가 충분하지 않으므로 아직 개선 수치를 주장하면 안 됨

**강점 키워드:** AI 품질 평가, 실험 설계, 정확도·비용·지연 동시 관리

### E. 도메인 이벤트 기반 성장 시스템

- Meal·Routine 도메인은 Streak·Badge 구현을 직접 호출하지 않고 사실 이벤트만 발행
- Growth 도메인이 이벤트를 구독해 보상 처리
- 동기 EventListener를 사용해 기록과 보상의 원자적 커밋·롤백 유지
- Streak가 실제 증가한 경우에만 후속 이벤트를 발행해 하루 중복 평가 방지
- Request-scoped 수집기로 해당 요청에서 획득한 Badge를 원래 응답에 함께 반환

**강점 키워드:** 도메인 분리, 이벤트 체이닝, 확장성, 원자성

### F. 새벽 4시 날짜 경계 버그 해결

- 자정~03:59 식사는 전날 기록으로 보는 도메인 규칙 존재
- 백엔드 일부 기능과 프론트 4개 화면이 달력 날짜를 사용해 데이터 불일치 발생
- Java `EffectiveDateResolver`와 JavaScript `getEffectiveToday()`로 규칙 통합
- 식단 등록, 사진 식단, 온보딩, 조회 기본값과 4개 화면에 동일 규칙 적용

**강점 키워드:** 분산된 비즈니스 규칙, 재현 기반 디버깅, 프론트·백엔드 계약

### G. 사진 식단 저장 시 스키마 변경 제거

- AI 추정 결과를 기존 MealItem 영양소 필드에 저장
- `foodCode=null`을 AI 추정 데이터의 구분자로 활용
- 예정했던 신규 컬럼 5개와 별도 엔티티를 추가하지 않음
- 기존 일일 영양소 합산 쿼리를 변경 없이 재사용

**강점 키워드:** 데이터 모델 재사용, 마이그레이션 위험 감소, YAGNI

## 8. 소재 우선순위

1. **AI 호출을 제거해 3~5초를 수십 ms로 단축한 의사결정**
   - 문제·판단·수치·성과가 가장 명확하다.
2. **RAG 개인화 챗봇 + 근거 반환 + 검색 임계값**
   - KB 자연어 검색·금융상담과 직접 연결된다.
3. **규칙 기반 동적 Agent 라우팅 + 조건부 RAG + fallback**
   - KB 멀티 에이전트 방향과 직접 연결된다.
4. **Redis 12시간 캐시 + 최대 15초 DB 커넥션 점유 방지**
   - 플랫폼 안정성과 비용 관점이 강하다.
5. **Vision AI 평가 파이프라인**
   - 실제 데이터셋으로 지표를 확보하면 가장 강한 AI 엔지니어링 소재가 될 수 있다.
6. **새벽 4시 날짜 경계 버그 해결**
   - 복잡한 실서비스 규칙과 E2E 디버깅 역량을 보여준다.
7. **도메인 이벤트 기반 성장 시스템**
   - AI보다는 백엔드·플랫폼 설계 역량을 강조할 때 적합하다.
