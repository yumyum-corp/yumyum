## ADR-1: DB 음식 검색 대신 Claude Vision 직접 영양소 추정

### Context
사진으로 식단 기록 시 음식 영양소를 얻는 방법 결정 필요.
- **Option A:** Claude Vision으로 음식 이름만 감지 → 식품안전처 DB에서 영양소 검색
- **Option B:** Claude Vision이 음식 이름 + 영양소를 한 번에 추정

### Decision
**Option B — Claude Vision 직접 추정**

### Rationale

> ⚠️ 아래 근거 중 첫 항목은 2026-09-12 실측으로 **반증됐다**. 결정 자체는
> 유지되지만 이유가 다르다. 이 절 끝의 「ADR-1 근거 정정」을 함께 읽을 것.

- **영양소 오차의 주요 원인은 계수가 아니라 그램 추정 오차**
  - DB 매칭 방식: Vision으로 감지한 음식명의 정확도 + DB 검색 정확도 + 그램 추정 오차
  - Vision 직접 추정: Vision의 그램 추정 오차만 발생
  - 최종 영양소 오차는 그램 추정 오차가 지배적 → 두 방식의 정확도 차이 미미
- **복합 한식 처리 용이**
  - 비빔밥, 찌개 등은 여러 재료가 혼합되어 있어 단일 음식명으로 DB 매칭 불가능
  - 재료를 분리해서 각각 검색 필요 → 추가 API 호출, 사용자 개입 필요
- **API 호출 횟수 감소**
  - Vision 1회 호출만으로 음식명 + 영양소 획득
  - DB 검색 방식은 Vision + N회 검색 필요
- **UX 단순화**
  - DB 불일치 또는 검색 실패 시 사용자 수동 확인 단계 제거
  - 한 번의 API 응답으로 완결성 있는 결과 제공

### Alternatives Considered
- **DB 검색:** 정확한 공식 데이터 사용 가능하나 복합 음식 처리 어렵고 UX가 끊김, API 호출 증가

### Consequences
- AI 추정값이므로 동일 음식도 사진 각도, 조명, 포션 차이에 따라 추정값이 달라질 수 있음
- `food_code IS NULL` 필터로 AI 추정 아이템 식별 가능
- Claude의 훈련 데이터 범위 내에서만 정확도 보장

## ADR-1 근거 정정 (2026-09-12)

**결정(Option B)은 유지한다. 근거가 틀렸다.**

ADR-1은 "영양소 오차의 주요 원인은 계수가 아니라 그램 추정 오차 → 두 방식의
정확도 차이 미미"라는 가정에 기댔다. 이 가정은 당시 측정된 적이 없었다.
`ai/eval/eval_photo_meal.py`로 실측한 결과 **가정은 틀렸고, 결론은 맞았다.**

### 측정 방법

같은 사진·같은 그램 추정 위에서 두 방식을 비교한다. Option A의 kcal을
`Vision이 추정한 그램 × MFDS 밀도`로 다시 계산하면 두 방식이 그램 추정을
공유하므로 **차이가 계수에서만** 나온다. 논쟁 중인 변수 그 자체다.

- 평가셋 31장 (`composite` 10 / `multi` 11 / `single` 10), 항목 20개
  (그램 정답 20 · kcal 정답 16 · 합계 kcal 정답 27장)
- 모델 `claude-opus-4-5-20251101`, 프로덕션 프롬프트 사본, 비용 $0.43
- kcal 정답은 포장 표기(`package`)에서만 취했다. MFDS에서 베낀 정답으로
  MFDS를 채점하면 순환논증이 되므로 출처를 라벨에 기록하고 분리했다.

### 결과 1 — 계수 오차는 미미하지 않다

| 지표 | MAPE | n |
| --- | --- | --- |
| 그램 | 29.60% | 15 |
| kcal | 37.48% | 12 |
| **밀도(kcal/g)** | **18.64%** | 12 |

밀도 오차는 그램을 소거한 **순수 계수 오차**다. `kcal = 그램 × 밀도`라
kcal 오차만 보면 두 오차가 부호 반대로 상쇄돼 작아 보일 수 있어, 계수를
따로 재야 판정이 선다.

계수 오차가 그램 오차의 **63%**다. ADR-1이 "미미하다"고 단정한 크기가 아니다.
그램이 더 크다는 방향만 맞았다.

### 결과 2 — DB 계수는 원리상 더 정확하다

A와 B 둘 다 값이 있는 항목만으로 짝지어 비교했다. arm별 전체 평균끼리 견주면
조회에 실패한 항목이 A에서만 빠져 표본이 어긋난다.

| 조합 | n | B(Vision) | A(MFDS) | A−B |
| --- | --- | --- | --- | --- |
| 감지명·정확일치 → 중앙값 **(현실)** | 7 | 30.39% | 29.96% | **−0.43** |
| 감지명·정확일치 → 오라클 **(상한)** | 7 | 30.39% | 16.12% | **−14.27** |
| 정답명·정확일치 → 중앙값 | 11 | 36.35% | 34.57% | −1.78 |

오라클은 정확일치 후보 중 정답 kcal에 가장 가까운 레코드를 고른 값이다.
달성 불가능한 상한이지만, **DB의 계수 자체는 Vision보다 14%p 정확하다**는
것을 보여준다.

### 결과 3 — 그 우위를 이름→레코드 해석이 전부 상쇄한다

현실 조건에서 두 방식은 동률(−0.43%p)이다. 상한과 현실 사이의 14%p를
메우는 것이 두 가지다.

**① 조회 실패.** Vision이 부르는 이름으로 MFDS 정확일치가 되는 경우가
60%뿐이다(실패 40%). Vision은 `닭가슴살 구이`·`삶은 달걀`·`흰쌀밥`처럼
수식어를 붙이거나 동의어를 쓴다.

**② 후보 모호성.** 찾아도 어느 레코드를 고를지 정할 수 없다. 정확일치가
평균 10.89건이고 kcal이 중앙값 기준 1.55배 흩어진다. `부대찌개`는 35건이
12~228 kcal/100g로 **19배** 벌어진다.

### 결과 4 — 매칭을 느슨하게 해도 구제되지 않는다

"`흰쌀밥`과 `쌀밥`은 같은 음식인데 실패로 세는 게 맞느냐"는 반론에 답하기
위해, 포함관계까지 인정하는 대조군을 같이 측정했다.

| 정책 | 조회 실패 | A의 kcal MAPE |
| --- | --- | --- |
| 정확일치만 | 40% | 29.96% |
| 포함관계 허용 | **7%** | **54.58%** |

실패는 줄지만 오차가 1.8배가 된다. 무엇이 붙는지 보면 이유가 분명하다.

| 감지명 | 포함관계로 붙는 레코드 | kcal/100g |
| --- | --- | --- |
| 삶은 달걀 | 삶은 달걀이 통째로 들어있는 **쫄면** | 228 |
| 스팸 | CJ 바삭**팝콘** 스팸맛 | 564 |
| 참치 | **김치찌개** 참치 | 51 |

`흰쌀밥` 하나만 보면 완화가 타당하다(「슈퍼우먼 흰쌀밥」 145로 맞다). 그러나
같은 규칙이 달걀을 쫄면으로, 스팸을 팝콘으로 만든다. **엄격하면 10건 중 4건을
못 찾고, 느슨하면 오차가 1.8배가 되는 양자택일이다.** 매칭 정책을 바꿔서
Option A를 구제할 수 없다.

### 정정된 근거

> **DB 조회는 계수가 정확해 원리상 14%p 우위가 있으나, 음식명→레코드 해석이
> 그 우위를 전부 상쇄한다. 엄격한 매칭은 40%를 찾지 못하고, 느슨한 매칭은
> 엉뚱한 음식을 집어 오차를 1.8배로 키운다. 실측상 두 방식은 대등하며,
> Vision 직접 추정이 API 호출 수와 UX에서 앞서므로 Option B를 유지한다.**

ADR-1의 나머지 근거는 이렇게 갈린다.

| 원래 근거 | 판정 |
| --- | --- |
| 계수 오차 미미 → 정확도 차이 미미 | **반증.** 계수는 14%p 차이 난다. 결론만 우연히 맞았다 |
| 복합 한식 처리 용이 | **약함.** 조회 실패율이 `composite` 33.3% vs 전체 40%로 오히려 낮다 |
| API 호출 횟수 감소 | **유지.** Option A는 이름 1개당 최대 40페이지를 훑어야 했다 |
| UX 단순화 | **강화.** 조회 실패 40%는 그만큼 사용자 개입이 필요하다는 뜻이다 |

"복합 한식은 단일 음식명으로 DB 매칭 불가능"은 DB 탓이 아니었다. 음식명 F1이
`single` 0.857 대 `composite` 0.185로, **Vision이 복합 음식을 한 덩어리로 보지
않고 구성요소로 분해한다**(덮밥 → 밥 + 고기). 문제는 DB가 아니라 Vision의
출력 단위가 DB 조회 단위와 어긋난다는 데 있다.

### 한계

- **짝지은 표본이 7~12개로 작다.** 항목 하나가 MAPE를 크게 흔든다. 결과 2·3의
  수치는 방향은 신뢰할 만하나 소수점을 인용할 크기가 아니다. 결과 1(n=12~15)과
  조회 실패율은 상대적으로 단단하다.
- 평가셋이 편의점 도시락·덮밥에 편중돼 있다. `single` 보강이 필요하다.
- 하네스 자체에서 측정 오류 세 건을 잡아 수치를 정정했다 — MFDS 스캔 상한(실패율
  35%→20% 과대평가), 검색어에 괄호 설명이 실리던 버그(40%→ 실제), Option A/B를
  서로 다른 표본으로 비교하던 결함(판정이 뒤집혔다). 측정 도구를 신뢰하기 전에
  도구를 먼저 의심해야 한다는 사례로 남긴다.

### 후속

- `single` 12장 보강 후 짝지은 표본을 19개로 올려 결과 2·3을 재측정한다.
- 개선 여지는 **그램 추정 프롬프트**에 있다(그램 MAPE 29.6%가 여전히 가장 크다).
  식기 크기를 근거로 쓰게 하는 `hinted` 프롬프트 대조군으로 검증한다.
- 재현: `cd ai && python -m eval.eval_photo_meal --dataset eval/dataset/labels.jsonl
  --prompt prod --yes-real-api --out eval/results/prod.json`

## ADR-2: 기존 MealItem 필드 재사용 (스키마 변경 없음)

### Context
AI 추정 아이템 저장 시 기존 MealItem 스키마를 확장할지 결정 필요.
초기 설계 시 5개 컬럼 추가(ai_estimated_flag, source_type 등)를 예정했으나 실제 엔티티 분석 후 재검토.

### Decision
기존 `calories`, `protein`, `carbs`, `fat` 필드를 AI 추정값으로 그대로 사용.
- `foodCode = null` (AI 추정 아이템 마커)
- `foodName = AI 감지 음식명`
- **스키마 변경 없음**

### Rationale
- **기존 필드 충분함**
  - MealItem의 영양소 필드(`calories`, `protein`, `carbs`, `fat`)는 이미 double 타입
  - JPA 기본값이 nullable이므로 foodCode null 상태에서도 영양소 저장 가능
- **마이그레이션 비용 제거**
  - 새 컬럼 5개 추가 시 Flyway 마이그레이션 필요
  - 기존 데이터 스키마 확장 비용 및 위험성 증가
- **합산 로직 분기 불필요**
  - `DailySummaryService`의 영양소 합산 쿼리는 foodCode와 무관하게 MealItem 필드 직접 합산
  - `SUM(protein), SUM(carbs), SUM(fat)` 같은 단순 집계만으로 처리
  - DB-level에서 AI 추정값과 DB 조회값을 동일하게 취급 가능
- **명시성 확보**
  - `MealItem.fromAiEstimate()` 팩토리 메서드 하나로 처리
  - 호출 처에서 AI 추정 아이템임이 명확히 드러남
  - 복잡도 제로

### Alternatives Considered
- **5개 컬럼 추가:** 명시적이지만 DB 마이그레이션 + 합산 로직 분기 처리 비용 발생
- **별도 AiMealItem 엔티티:** 과도한 복잡도 증가, 합산 로직 이원화, 쿼리 복잡도 증가

### Consequences
- `foodCode IS NULL` 쿼리로 AI 추정 아이템만 식별 필요
- AI 아이템의 `fiber`는 0.0으로 저장 (Claude Vision이 식이섬유를 추정하지 않음)
- 향후 AI 아이템 통계/분석이 필요하면 `foodCode` 필터링으로 구분

## ADR-3: 이미지를 multipart 대신 base64 JSON으로 전송

### Context
Vue → Spring 이미지 전송 방식 결정.
- **Option A:** `multipart/form-data`로 바이너리 전송 (네트워크 효율적)
- **Option B:** FileReader API로 base64 변환 후 JSON body로 전송 (형식 일관성)

### Decision
**Option B — base64 JSON**

### Rationale
- **기존 apiClient 호환성**
  - 현재 `apiClient.post()`는 JSON body 전용으로 구현됨
  - multipart 지원 추가 시 별도 메서드 작성 또는 전체 apiClient 수정 필요
  - Vue 프로젝트에서 이미 모든 API 호출이 JSON 기반 → 추가 API 메서드는 인증 로직 중복
- **Content-Type 충돌 회피**
  - apiClient가 자동으로 `Content-Type: application/json` 설정
  - multipart 사용 시 FormData 객체의 boundary 자동 생성을 apiClient가 방해할 수 있음
  - base64는 Content-Type 걱정 없이 일반 JSON body로 전송
- **FastAPI 호환성**
  - FastAPI도 JSON 전용 처리
  - Spring → FastAPI 전달 시 base64 문자열을 그대로 전달 가능
  - 형식 변환 없이 end-to-end 일관성 유지
- **모바일 사진 범위 내 실용성**
  - 일반적인 모바일 사진 1~3MB → base64 인코딩 후 ~4MB
  - Vue에서 클라이언트 사이드 검증으로 10MB 초과 차단 가능
  - 실용적 범위 내에서 네트워크 오버헤드 허용 가능

### Alternatives Considered
- **multipart/form-data:**
  - 장점: 네트워크 효율적 (base64 대비 ~25% 더 작음)
  - 단점: apiClient 수정 필요, Spring에서 MultipartFile 처리 및 base64 디코딩 추가 코드 필요
- **별도 fetch 직접 호출:**
  - 장점: multipart 네이티브 지원
  - 단점: apiClient의 인증 로직(JWT 헤더 자동 추가) 우회 → 토큰 처리 중복 발생

### Consequences
- 10MB 파일은 base64로 ~13.3MB → Vue에서 클라이언트 사이드 검증으로 10MB 상한 설정
- Spring 메모리에 base64 문자열 일시 상주 (최대 ~13MB)
  - base64 디코딩 후 즉시 FastAPI로 전달하여 메모리 해제
- 초저속 네트워크에서는 multipart 대비 ~33% 더 느린 전송 시간 (mobile 4G 환경에서 체감 차이 미미)
