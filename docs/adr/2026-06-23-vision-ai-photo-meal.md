**Date:** 2026-06-23  
**Status:** Accepted (ADR-1은 2026-09-12 측정으로 **근거 정정**, 결정은 유지)

## ADR-1: DB 음식 검색 대신 Claude Vision 직접 영양소 추정

### Context
사진으로 식단 기록 시 음식 영양소를 얻는 방법 결정 필요.
- **Option A:** Claude Vision으로 음식 이름만 감지 → 식품안전처 DB에서 영양소 검색
- **Option B:** Claude Vision이 음식 이름 + 영양소를 한 번에 추정

### Decision
**Option B — Claude Vision 직접 추정**

### Rationale

> ⚠️ 아래 근거 중 첫 항목은 2026-09-12 실측으로 **반증됐다**. 결정 자체는
> 유지되지만 이유가 다르다. 이 절 끝의 「ADR-1 근거 정정」을 함께 읽을 것.

- **영양소 오차의 주요 원인은 계수가 아니라 그램 추정 오차**
  - DB 매칭 방식: Vision으로 감지한 음식명의 정확도 + DB 검색 정확도 + 그램 추정 오차
  - Vision 직접 추정: Vision의 그램 추정 오차만 발생
  - 최종 영양소 오차는 그램 추정 오차가 지배적 → 두 방식의 정확도 차이 미미
- **복합 한식 처리 용이**
  - 비빔밥, 찌개 등은 여러 재료가 혼합되어 있어 단일 음식명으로 DB 매칭 불가능
  - 재료를 분리해서 각각 검색 필요 → 추가 API 호출, 사용자 개입 필요
- **API 호출 횟수 감소**
  - Vision 1회 호출만으로 음식명 + 영양소 획득
  - DB 검색 방식은 Vision + N회 검색 필요
- **UX 단순화**
  - DB 불일치 또는 검색 실패 시 사용자 수동 확인 단계 제거
  - 한 번의 API 응답으로 완결성 있는 결과 제공

### Alternatives Considered
- **DB 검색:** 정확한 공식 데이터 사용 가능하나 복합 음식 처리 어렵고 UX가 끊김, API 호출 증가

### Consequences
- AI 추정값이므로 동일 음식도 사진 각도, 조명, 포션 차이에 따라 추정값이 달라질 수 있음
- `food_code IS NULL` 필터로 AI 추정 아이템 식별 가능
- Claude의 훈련 데이터 범위 내에서만 정확도 보장

## ADR-1 근거 정정 (2026-09-12)

**결정(Option B)은 유지한다. 근거는 반증됐다.**

ADR-1은 "영양소 오차의 주요 원인은 계수가 아니라 그램 추정 오차 → 두 방식의
정확도 차이 미미"라는 가정에 기댔다. 이 가정은 당시 측정된 적이 없었다.
`ai/eval/eval_photo_meal.py`로 실측한 결과 **가정은 틀렸고, 결론은 맞았다.**

### 측정 방법

같은 사진·같은 그램 추정 위에서 두 방식을 비교한다. Option A의 kcal을
`Vision이 추정한 그램 × MFDS 밀도`로 다시 계산하면 두 방식이 그램 추정을
공유하므로 **차이가 계수에서만** 나온다. 논쟁 중인 변수 그 자체다.

- 평가셋 31장 (`composite` 10 / `multi` 11 / `single` 10), 항목 20개.
  직접 촬영했다. 공개 데이터셋(AI Hub 「음식 이미지 및 영양정보 텍스트」)은
  양 정보가 그램이 아닌 Q1~Q5 등급 분류라 그램 오차를 잴 수 없었다.
- 모델 `claude-opus-4-5-20251101`, 프로덕션 프롬프트 사본, 31장당 $0.43
- kcal 정답은 포장 표기(`package`)에서만 취했다. MFDS에서 베낀 정답으로
  MFDS를 채점하면 순환논증이 되므로 출처를 라벨에 기록하고 분리했다.
- A와 B 둘 다 값이 있는 항목만으로 **짝지어** 비교한다. arm별 전체 평균끼리
  견주면 조회에 실패한 항목이 A에서만 빠져 표본이 어긋난다.

### 결과 1 — 계수 오차는 미미하지 않다

| 지표 | `prod` | `dedup` |
| --- | --- | --- |
| 그램 MAPE | 27.39% (n=16) | 19.04% (n=17) |
| kcal MAPE | 34.07% (n=13) | 20.84% (n=14) |
| **밀도(kcal/g) MAPE** | **23.97%** (n=13) | **22.36%** (n=14) |

밀도 오차는 그램을 소거한 **순수 계수 오차**다. `kcal = 그램 × 밀도`라
kcal 오차만 보면 두 오차가 부호 반대로 상쇄돼 작아 보일 수 있어, 계수를
따로 재야 판정이 선다.

`prod`에서 계수 오차가 그램 오차의 **88%**다. ADR-1이 "미미하다"고 단정한
크기가 아니다. 더 결정적인 것은 `dedup`(결과 5)이다 — 중복 출력을 고치자
그램 오차가 19.04%로 떨어지면서 **계수 오차(22.36%)가 그램 오차보다 커졌다.**
"그램이 지배적"이라는 전제 자체가 성립하지 않는다.

### 결과 2 — DB 계수는 원리상 더 정확하다

`prod` 기준 짝지은 비교:

| 조합 | n | B(Vision) | A(MFDS) | A−B |
| --- | --- | --- | --- | --- |
| 감지명·정확일치 → 중앙값 **(현실)** | 8 | 25.22% | 21.20% | −4.02 |
| 감지명·정확일치 → 오라클 **(상한)** | 8 | 25.22% | 12.01% | **−13.21** |
| 정답명·정확일치 → 중앙값 | 12 | 32.74% | 31.05% | −1.70 |

오라클은 정확일치 후보 중 정답 kcal에 가장 가까운 레코드를 고른 값이다.
달성 불가능한 상한이지만, **DB의 계수 자체는 Vision보다 13%p 정확하다**는
것을 보여준다.

### 결과 3 — 그 우위를 이름→레코드 해석이 상쇄한다

상한과 현실 사이의 13%p를 메우는 것이 둘이다.

**① 조회 실패 37.5%.** Vision이 부르는 이름으로 MFDS 정확일치가 되는 경우가
62.5%뿐이다. Vision은 `닭가슴살 구이`·`삶은 달걀`·`흰쌀밥`처럼 수식어를
붙이거나 동의어를 쓴다.

**② 후보 모호성.** 찾아도 어느 레코드를 고를지 정할 수 없다. 정확일치가
평균 9.9건이고 kcal이 중앙값 기준 1.55배 흩어진다. `부대찌개`는 35건이
12~228 kcal/100g로 **19배** 벌어진다.

### 결과 4 — 매칭을 느슨하게 해도 구제되지 않는다

"`흰쌀밥`과 `쌀밥`은 같은 음식인데 실패로 세는 게 맞느냐"는 반론에 답하기
위해, 포함관계까지 인정하는 대조군을 같이 측정했다.

| 정책 | 조회 실패 | 후보 수 | 모호도 | A의 kcal MAPE |
| --- | --- | --- | --- | --- |
| 정확일치만 | 37.5% | 9.9건 | 1.55배 | **21.20%** |
| 포함관계 허용 | 6.2% | 989.8건 | 89.7배 | **46.82%** |

실패는 줄지만 오차가 2.2배가 된다. 무엇이 붙는지 보면 이유가 분명하다.

| 감지명 | 포함관계로 붙는 레코드 | kcal/100g |
| --- | --- | --- |
| 삶은 달걀 | 삶은 달걀이 통째로 들어있는 **쫄면** | 228 |
| 스팸 | CJ 바삭**팝콘** 스팸맛 | 564 |
| 참치 | **김치찌개** 참치 | 51 |

`흰쌀밥` 하나만 보면 완화가 타당하다(「슈퍼우먼 흰쌀밥」 145로 맞다). 그러나
같은 규칙이 달걀을 쫄면으로, 스팸을 팝콘으로 만든다. **엄격하면 10건 중 4건을
못 찾고, 느슨하면 오차가 2.2배가 되는 양자택일이다.** 매칭 정책을 바꿔서
Option A를 구제할 수 없다.

### 결과 5 — 측정이 제품 결함을 찾았다: 이중 계산

`prod`에서 합계 kcal 편향이 **평균 +20.4%**로 과대추정에 쏠려 있었고, 정답의
1.5배를 넘는 사진이 31장 중 5장이었다. 예측을 뜯어보니 원인이 드러났다.

```
0004 가츠동 예측:
  카츠동 (돈카츠 덮밥)                      ← 요리 전체
  돈카츠, 계란, 흰쌀밥, 양파, 홍생강, 파    ← 그 구성요소
  → 합계 kcal 정답의 1.97배
```

**요리 전체와 구성요소를 동시에 출력한다.** 앱은 항목 kcal을 합산해 사용자에게
총 칼로리로 보여주므로, 사용자 기록이 두 배로 남는 결함이다.

초판 정정에서는 이 현상을 "Vision이 복합 음식을 구성요소로 **분해**한다"고
적었는데 틀렸다. 분해와 중복은 처방이 다르다 — 분해라면 DB 조회 단위 문제지만,
중복이라면 프롬프트 제약으로 풀린다. 미검출 4건을 뜯어보면 성격이 갈린다.

| 사진 | 예측 | 성격 |
| --- | --- | --- |
| 0004 가츠동 | `카츠동` + 구성요소 6개 | **중복 출력** |
| 0015 사케동 | `연어 사시미, 백미밥, 무채…` (요리명 없음) | 순수 분해 |
| 0026 쫄면 | `비빔밥` + 구성요소 7개 | 오인식 + 중복 |
| 0033 해물야끼우동 | `명란 크림 파스타` + 새우, 쪽파 | 오인식 + 중복 |

"요리명 + 구성요소" 동시 출력이 4건 중 3건으로 지배적이고, 순수 분해는 1건뿐이다.

### 결과 6 — 프롬프트 한 줄로 Option B가 Option A를 역전했다

이 실험의 `dedup` 프롬프트는 당시 `prod`와 **단 한 가지**만 다르다.
결과가 좋아 채택했으므로, 지금은 `dedup`이 `prod`이고 당시의 `prod`는
`prod_v1`로 남아 있다(아래 표의 열 이름은 측정 당시 기준). 요리 전체와 구성 재료를
동시에 나열하지 말라는 제약이다(`multi`를 망가뜨리지 않도록 양방향으로 지시).
그램 힌트가 섞이면 개선을 귀인할 수 없어 `hinted`와 따로 뒀다.

| 지표 | `prod` | `dedup` |
| --- | --- | --- |
| 음식명 F1 | 0.377 | **0.773** |
| precision | 0.246 | **0.708** |
| 과검출 | 49건 | **7건** |
| 그램 MAPE | 27.39% | **19.04%** |
| kcal MAPE | 34.07% | **20.84%** |
| 합계 kcal 편향 | +20.4% | **+12.5%** |
| 이중 계산 의심 | 5장 | **2장** |
| `composite` F1 | 0.219 | **0.667** |
| 지연 · 비용 | 6111ms · $0.433 | 5198ms · $0.405 |

과검출이 49건에서 7건으로 줄었다. `composite` F1이 낮았던 주원인이 중복
출력이었음이 확인된다. 출력 토큰이 줄어 지연과 비용도 함께 내려갔다.

그리고 A/B 판정이 뒤집혔다.

| 짝지은 비교 (감지명·정확 → 중앙값) | n | B(Vision) | A(MFDS) | A−B |
| --- | --- | --- | --- | --- |
| `prod` | 8 | 25.22% | 21.20% | −4.02 (A 우세) |
| `dedup` | 9 | 24.70% | 28.05% | **+3.35 (B 우세)** |

**Option B에는 프롬프트라는 개선 여지가 있고 Option A에는 없다.** 오히려
`dedup`은 Option A를 악화시켰다(조회 실패 37.5%→41.2%) — 출력이 요리명
단위가 되면서 `가츠동` 같은 복합 요리명이 늘었고, 그런 이름일수록 DB에 없다.

### 정정된 근거

> **DB 조회는 계수가 정확해 원리상 13%p 우위가 있으나, 음식명→레코드 해석이
> 그 우위를 상쇄한다. 엄격한 매칭은 37.5%를 찾지 못하고, 느슨한 매칭은 엉뚱한
> 음식을 집어 오차를 2.2배로 키운다. 나아가 Option B는 프롬프트로 개선되지만
> (F1 0.377→0.773) Option A는 그 개선으로 오히려 나빠진다. 따라서 Option B를
> 유지한다.**

ADR-1의 원래 근거 넷은 이렇게 갈린다.

| 원래 근거 | 판정 | 측정 |
| --- | --- | --- |
| 계수 오차 미미 → 정확도 차이 미미 | **반증** | 계수 오차가 그램 오차의 88%, `dedup`에서는 그램보다 크다 |
| 복합 한식 처리 용이 | **부분 유지, 이유가 다름** | DB 조회 실패율은 `composite` 33.3% < 전체 37.5%로 낮다. 진짜 문제는 Vision의 중복 출력이었고 프롬프트로 해결됐다 |
| API 호출 횟수 감소 | **유지** | Option A는 이름 1개당 최대 40페이지 조회가 필요했다 |
| UX 단순화 | **강화** | 조회 실패 37.5%는 그만큼 사용자 개입이 필요하다는 뜻이다 |

### 한계

- **짝지은 표본이 8~13개로 작다.** 같은 프롬프트·같은 사진으로 두 번 돌렸는데
  밀도 MAPE가 18.64%와 23.97%로 벌어졌다(모델 비결정성 + 라벨 보정이 섞여
  분리되지 않는다). 방향은 신뢰할 만하나 소수점을 인용할 크기가 아니다.
- 평가셋이 편의점 도시락·덮밥에 편중돼 있다. `single` 보강이 필요하다.
- `multi` 11장은 포장이 총량만 주어 항목별 정답이 없다(`total_only`). 합계
  kcal 지표에만 기여한다.
- **하네스 자체에서 측정 오류 넷을 잡아 수치를 정정했다.** MFDS 스캔 상한이
  낮아 실패율이 35%로 과대평가된 것, 검색어에 괄호 설명이 실려 조회가 0건
  나던 것, Option A/B를 서로 다른 표본으로 비교해 판정이 뒤집혔던 것, 원시
  예측을 저장하지 않아 라벨 수정 후 재채점이 불가능했던 것. 측정 도구를
  신뢰하기 전에 도구를 먼저 의심해야 한다는 사례로 남긴다.

  쪽에서는 덜 먹는다 — 별도 처방이 필요하다.
- `single` 12장 보강 후 짝지은 표본을 19개로 올려 결과 2·6을 재측정한다.
- 그램 추정 힌트(`hinted`) 대조군은 미측정이다. `dedup` 이후 그램 MAPE가
  19.04%로 내려갔으므로 개선 여지가 줄었을 수 있다.
- 재현: `cd ai && python -m eval.eval_photo_meal --dataset eval/dataset/labels.jsonl
  --prompt prod --yes-real-api --out eval/results/prod.json`
  (`--prompt dedup`으로 대조군, `--compare`로 비교)

## ADR-2: 기존 MealItem 필드 재사용 (스키마 변경 없음)

### Context
AI 추정 아이템 저장 시 기존 MealItem 스키마를 확장할지 결정 필요.
초기 설계 시 5개 컬럼 추가(ai_estimated_flag, source_type 등)를 예정했으나 실제 엔티티 분석 후 재검토.

### Decision
기존 `calories`, `protein`, `carbs`, `fat` 필드를 AI 추정값으로 그대로 사용.
- `foodCode = null` (AI 추정 아이템 마커)
- `foodName = AI 감지 음식명`
- **스키마 변경 없음**

### Rationale
- **기존 필드 충분함**
  - MealItem의 영양소 필드(`calories`, `protein`, `carbs`, `fat`)는 이미 double 타입
  - JPA 기본값이 nullable이므로 foodCode null 상태에서도 영양소 저장 가능
- **마이그레이션 비용 제거**
  - 새 컬럼 5개 추가 시 Flyway 마이그레이션 필요
  - 기존 데이터 스키마 확장 비용 및 위험성 증가
- **합산 로직 분기 불필요**
  - `DailySummaryService`의 영양소 합산 쿼리는 foodCode와 무관하게 MealItem 필드 직접 합산
  - `SUM(protein), SUM(carbs), SUM(fat)` 같은 단순 집계만으로 처리
  - DB-level에서 AI 추정값과 DB 조회값을 동일하게 취급 가능
- **명시성 확보**
  - `MealItem.fromAiEstimate()` 팩토리 메서드 하나로 처리
  - 호출 처에서 AI 추정 아이템임이 명확히 드러남
  - 복잡도 제로

### Alternatives Considered
- **5개 컬럼 추가:** 명시적이지만 DB 마이그레이션 + 합산 로직 분기 처리 비용 발생
- **별도 AiMealItem 엔티티:** 과도한 복잡도 증가, 합산 로직 이원화, 쿼리 복잡도 증가

### Consequences
- `foodCode IS NULL` 쿼리로 AI 추정 아이템만 식별 필요
- AI 아이템의 `fiber`는 0.0으로 저장 (Claude Vision이 식이섬유를 추정하지 않음)
- 향후 AI 아이템 통계/분석이 필요하면 `foodCode` 필터링으로 구분

## ADR-3: 이미지를 multipart 대신 base64 JSON으로 전송

### Context
Vue → Spring 이미지 전송 방식 결정.
- **Option A:** `multipart/form-data`로 바이너리 전송 (네트워크 효율적)
- **Option B:** FileReader API로 base64 변환 후 JSON body로 전송 (형식 일관성)

### Decision
**Option B — base64 JSON**

### Rationale
- **기존 apiClient 호환성**
  - 현재 `apiClient.post()`는 JSON body 전용으로 구현됨
  - multipart 지원 추가 시 별도 메서드 작성 또는 전체 apiClient 수정 필요
  - Vue 프로젝트에서 이미 모든 API 호출이 JSON 기반 → 추가 API 메서드는 인증 로직 중복
- **Content-Type 충돌 회피**
  - apiClient가 자동으로 `Content-Type: application/json` 설정
  - multipart 사용 시 FormData 객체의 boundary 자동 생성을 apiClient가 방해할 수 있음
  - base64는 Content-Type 걱정 없이 일반 JSON body로 전송
- **FastAPI 호환성**
  - FastAPI도 JSON 전용 처리
  - Spring → FastAPI 전달 시 base64 문자열을 그대로 전달 가능
  - 형식 변환 없이 end-to-end 일관성 유지
- **모바일 사진 범위 내 실용성**
  - 일반적인 모바일 사진 1~3MB → base64 인코딩 후 ~4MB
  - Vue에서 클라이언트 사이드 검증으로 10MB 초과 차단 가능
  - 실용적 범위 내에서 네트워크 오버헤드 허용 가능

### Alternatives Considered
- **multipart/form-data:**
  - 장점: 네트워크 효율적 (base64 대비 ~25% 더 작음)
  - 단점: apiClient 수정 필요, Spring에서 MultipartFile 처리 및 base64 디코딩 추가 코드 필요
- **별도 fetch 직접 호출:**
  - 장점: multipart 네이티브 지원
  - 단점: apiClient의 인증 로직(JWT 헤더 자동 추가) 우회 → 토큰 처리 중복 발생

### Consequences
- 10MB 파일은 base64로 ~13.3MB → Vue에서 클라이언트 사이드 검증으로 10MB 상한 설정
- Spring 메모리에 base64 문자열 일시 상주 (최대 ~13MB)
  - base64 디코딩 후 즉시 FastAPI로 전달하여 메모리 해제
- 초저속 네트워크에서는 multipart 대비 ~33% 더 느린 전송 시간 (mobile 4G 환경에서 체감 차이 미미)
